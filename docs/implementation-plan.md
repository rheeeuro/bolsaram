## 설계 문서와 달라진 결정

설계 문서는 Supabase(PostgreSQL/Auth/Storage/RLS)를 전제하지만, 이 저장소의 고정
인프라는 로컬 컨테이너다. 사용자 확인을 거쳐 다음과 같이 대체했다.

| 설계 문서           | 이 구현                                                                          | 이유                                                                                |
| ------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Supabase PostgreSQL | 로컬 `postgres:17` (`127.0.0.1:5442`)                                            | 외부 계정·키 없이 전체 플로우를 실제로 돌려 검증하기 위해                           |
| Supabase Auth       | 자체 세션(서명 쿠키 + `sessions` 테이블), 관리자 이메일/비밀번호 · 회원 전화 OTP | 동일                                                                                |
| Supabase Storage    | 로컬 private 디렉터리 + HMAC signed URL                                          | 동일                                                                                |
| Supabase RLS        | Postgres RLS 그대로 사용                                                         | 대체하지 않았다. `bolsaram_app` 롤은 `NOBYPASSRLS` 이며 모든 접근이 정책을 통과한다 |
| OpenAI multimodal   | provider 추상화, 기본 `mock`                                                     | `OPENAI_API_KEY` 가 있으면 `AI_PROVIDER=openai` 로 전환                             |
| Expo 모바일 앱      | 이번 범위 제외. spike 계획 문서 + 웹 Import 우선                                 | 실기기 검증 없이 share 동작을 확정할 수 없다(설계문서 §15-0)                        |

기존 MariaDB(`3308`)는 v1 프로토타입용이며 `docker compose --profile legacy` 로만 뜬다.
백엔드 포트 `8010` 은 쓰지 않는다 — API 가 Next.js Route Handler 로 웹 앱(`3020`) 안에 있다.

- Discover 필터 전 항목, 한국어 자유 검색.

- Import: 세션 생성 → signed upload(미인증 401 / 서명 위조 403) → mock 추출 → 검토 → commit.
- 같은 세션 commit 2회 호출 시 동일 프로필 반환(`reused: true`).

- 초대 발급 → claim → 재사용 거부. 평문 토큰은 DB에 없음.
- signed URL: 유효 200 / 비로그인 401 / 변조 403 / 만료 410 / 경로 탈출 403, `cache-control: private, no-store`.

브라우저 스크린샷은 찍지 못했습니다 — 이 호스트에 Chromium 실행에 필요한 시스템 라이브러리(`libatk-1.0`)가

있고, `production` 으로 올리면 서버가 그 조합을 거부한다.

배포 스크립트 이름을 `deploy` → `deploy:web` 으로 바꿨다(2026-09-07). pnpm 9 에 내장 `deploy`
명령이 있어 `pnpm deploy` 가 스크립트 대신 그쪽으로 잡히고 `ERR_PNPM_NOTHING_TO_DEPLOY` 로
끝났다. `pnpm run deploy` 로 우회할 수는 있지만, 짧은 형태를 습관적으로 치면 계속 걸리므로
이름 자체를 겹치지 않게 했다. `pm2:*`·`db:*` 와 같은 접두 규칙에도 맞는다.
턴 종료 훅(`deploy-on-stop.sh`)은 `pnpm build` 와 `pm2 restart` 를 직접 부르므로 영향이 없다.

## 카카오 챗봇 Import 설계 변경 폐기 (2026-09-07)

`docs/v2/BOLSARAM_ARCHITECTURE_CHANGE_CHATBOT_v1.md` 는 Import 1차 채널을 모바일 Share
에서 카카오 챗봇으로 바꾸자는 설계 변경이었다. **채택하지 않았다.**

폐기 이유는 카카오 공식 스펙이다. 카카오 i 오픈빌더 스킬 요청의 `userRequest` 에는
`block` · `user` · `utterance` · `params` · `lang` · `timezone` 만 있고 사용자가 보낸
이미지·미디어·첨부파일을 전달하는 필드가 없다. 즉 그 문서 §4.1 의 핵심 흐름인
「사진 여러 장 전송 → Chatbot Webhook → ImportSession」이 오픈빌더로는 성립하지 않는다.
사용자 전송 이미지를 webhook 으로 받는 카카오 제품은 상담톡이며 파트너사 연동과 별도
계약이 필요하다 — 자체 스킬 서버만으로는 불가능하다.

따라서 Import 채널은 기존 구현을 유지한다: 관리자 웹 직접 업로드 + 원문 붙여넣기 +
AI 추출 + 관리자 검토. `import_source` enum 에 `KAKAO_CHATBOT` 을 추가하지 않았고
`chatbot_conversations` · `ProcessedExternalEvent` 같은 테이블도 만들지 않았다.
모바일 Share 의 우선순위도 내리지 않는다(원래 §10 단계로 미착수 상태다).

이 판단이 뒤집히는 조건은 하나다 — 상담톡 파트너 연동 계약이 생기고 실제 payload 와
이미지 URL lifetime 을 PoC 로 확인한 경우. 그때는 기존 Import 도메인을 그대로 두고
입력 Adapter 만 추가하는 그 문서의 방향(§7·§8)이 여전히 맞다.

## 텔레그램 Import 채널 (2026-09-07 추가)

`docs/v2/BOLSARAM_ARCHITECTURE_CHANGE_TELEGRAM_v1.md` 를 구현했다. Import 1차 채널을
모바일 OS Share 에서 텔레그램 봇으로 옮기는 설계 변경이다.

같은 날 폐기한 카카오 챗봇안(위 절)과 달리 이건 **공식 스펙으로 구현 가능하다.**

되돌아와 발신자 확인 수단이 된다. 파일 상한은 20MB, 다운로드 링크는 최소 1시간 유효하다.

### webhook 이 RLS 를 우회하지 않게 만든 방법

webhook 에는 세션 쿠키가 없다. 그렇다고 owner 커넥션으로 Import 를 쓰면
「service-role 을 인증 레이어 밖에서 쓰지 않는다」가 깨진다. 그래서 둘로 쪼갰다.

```
owner 커넥션 (인증 레이어, server/auth/telegram.ts)
  update_id 선점 · 연결 코드 소비 · 텔레그램 계정 → 주선자 신원 확인
        ↓ 신원 확정
withRls(주선자) — 그 뒤 전부. 일반 관리자 요청과 완전히 같다.
```

`telegram_link_codes` · `telegram_webhook_events` 는 `sessions`·`login_codes` 와 같은
취급이다 — 정책을 주지 않고 `REVOKE` 로 런타임 롤 권한을 회수했다. 0001 의
`ALTER DEFAULT PRIVILEGES` 가 새 테이블에 자동으로 권한을 주므로 명시적 회수가 필요했다.
`tests/telegram-import.test.ts` 의 「런타임 롤은 …접근할 수 없다」가 이걸 지킨다.

### at-most-once 를 골랐다

`update_id` 선점을 **처리 전에** 한다. 처리 중 실패하면 그 update 는 다시 오지 않는다
(행은 `processed_at IS NULL` 로 남아 조사에 쓴다). 반대로 처리 후에 선점하면 재전송이
사진을 두 번 저장한다.

의도적으로 이쪽을 골랐다 — 사진이 중복되면 프로필이 조용히 망가지는데, 유실되면 봇이
운영자에게 실패를 알리고 다시 보내면 된다. 설계 문서 §18 이 요구하는 것도 중복 방지다.

연결 코드는 `INVITE_TOKEN_PEPPER` 를 재사용하되 `telegram-link:` 접두어로 용도를 갈랐다.
새 필수 시크릿을 늘리지 않으면서 한쪽 해시를 다른 쪽에 쓸 수 없게 한다.

### 앨범 사진의 순서

앨범은 여러 webhook 으로 거의 동시에 도착한다. `MAX(sort_order) + 1` 로 번호를 매기면
같은 번호를 잡아 `UNIQUE (import_session_id, sort_order)` 에 걸리거나 서로를 덮어쓴다.
`appendUploadedAsset` 이 세션 행을 `FOR UPDATE` 로 먼저 잠가 직렬화한다 — 재시도 대신
도착 순서를 그대로 보존하는 쪽을 골랐다. 잠금을 빼면
`tests/telegram-import.test.ts` 「같은 앨범이 동시에 들어와도」가 실패한다(확인함).

### 문서 동기화

`tests/docs-guide.test.ts` 에 봇 정책 숫자(연결 코드 15분 · 사진 20MB · 대화 만료 24시간)와

### Node fetch 가 텔레그램에만 실패했던 것 (2026-09-07)

토큰을 넣고 처음 실제 호출을 했을 때 `getBotUsername()` 이 `fetch failed / ETIMEDOUT`
으로 실패했다. 같은 호스트에서 `curl` 은 정상이고, Node `fetch` 는 GitHub·npm 에는
붙는데 `api.telegram.org` 에만 실패했다.

원인은 IPv6 가 아니라 **연결 지연**이었다. Node 의 Happy Eyeballs 는 주소 하나당
`autoSelectFamilyAttemptTimeout`(기본 **250ms**)만 기다리고 다음 주소로 넘어간다.
`api.telegram.org`(암스테르담) 은 이 호스트에서 TCP 연결에 **260~266ms** 걸려 시도가
완료 직전에 취소된다. GitHub 는 6ms(로컬 엣지)라 걸리지 않았다.

`startup-node.ts` 에서 이 값을 2초로 올렸다. 주소 선택 방식은 건드리지 않았다 —
`--dns-result-order=ipv4first` 는 효과가 없었고(문제가 주소 선택이 아니므로),
IPv4 를 강제하는 대신 느린 연결을 허용하는 쪽이 원인에 맞는 처방이다.
OpenAI 처럼 해외 프로바이더 호출 전부가 같은 제한에 걸리므로 함께 해결된다.

이 과정에서 `instrumentation.ts` 를 런타임별로 갈랐다(`startup-node.ts`). Edge 런타임에서도
평가되는 파일에서 `node:net` 을 직접 import 하면 번들러가 경고한다 — Next 문서
「Specifying the runtime」이 안내하는 분리 방식을 따랐다.

`/api/admin/telegram` 이 `getBotUsername()` 실패를 `.catch(() => null)` 로 조용히
삼키고 있어서 원인을 찾을 수 없었다. 이유를 로그에 남기도록 고쳤다 — 토큰 오설정을
말없이 넘기면 딥링크만 사라진 채로 아무 단서가 없다.

### 남은 일

봇(`@bolsaram_bot`)과 `.env` 설정은 끝났고 여기까지 실제로 확인했다.

- `getMe` 로 토큰 유효성 확인, 관리자 화면의 연결 코드 발급이 실제 Bot API 를 거쳐
  `https://t.me/bolsaram_bot?start=<코드>` 딥링크를 만든다

  같은 `update_id` 재전송은 DB 에 행 하나만 남고 무시, 잘못된 JSON 도 200
- 로그에 프로필 원문·토큰이 남지 않음

**남은 것은 텔레그램이 우리 서버에 도달하는 구간이다.** 아래를 사람이 해야 한다.

1. 공개 HTTPS 주소 확보 — 현재 `APP_ORIGIN` 이 `127.0.0.1` 이라 텔레그램이 도달할 수 없다
2. `APP_ORIGIN` 을 그 주소로 바꾸고 `pnpm deploy:web`
3. `setWebhook` 등록 —
   `https://api.telegram.org/bot<token>/setWebhook?url=<origin>/api/integrations/telegram/webhook&secret_token=<secret>`
   (`<secret>` 은 `.env` 의 `TELEGRAM_WEBHOOK_SECRET` 값)
4. 관리자 화면 → Import Inbox → 텔레그램 연결 → 딥링크 또는 `/start <코드>`
5. 사진 여러 장 → 프로필 글 → Inbox 에 올라오는지 확인

`BUTTON_URL_INVALID` 아님). 봇이 무엇으로 해석하고 무엇을 답했는지는
`텔레그램 수신: …` / `텔레그램 응답: …` 로그로 남긴다(내용은 남기지 않는다).

### 사진을 모델에 보내지 않는다 (2026-09-07 결정)

프로필은 **항상 카카오톡에서 복사한 텍스트로 들어온다**(운영 확인). 스크린샷으로 오는
경우는 없다. 그래서 추출 입력에서 이미지를 제거했다 — `ExtractionInput` 에 이미지
필드 자체가 없고, `openai.ts` 의 `ContentPart` 도 텍스트만 표현한다. 조건부로 두면
언젠가 조건이 뒤집히므로 타입에서 막았다.

**실측으로 확인한 것 — 사진은 기여가 없었다.** 같은 세션(사진 3장 + 원문 81자)을
사진을 보낸 채로 한 번, 보내지 않고 한 번 분석했다.

| 실행                | 채운 필드 | 필드 목록                        |
| ------------------- | --------- | -------------------------------- |
| 사진 3장 함께 전송  | 11/16     | birthYear, height, hobbies, idealTypeText, jobCategory, jobTitle, mbti, religion, residenceRegion, smoking, workplaceRegion |
| 사진 미전송         | 11/16     | **동일**                         |

토큰 실측으로는 `detail:"low"` 도 이미지 크기에 따라 늘어난다 — 320×400 은 장당 156,
1200×1600 은 230 토큰이다(고정 비용이라는 통념과 다르다). 실제 사진은 후자에 가까워
4장이면 600~900 토큰이며, 원문 81자는 수십 토큰이다. 즉 **입력의 대부분이 아무것도
기여하지 않는 사진이었다.**

비용보다 중요한 것은 개인정보 경로다. 설계 변경 문서 §15 의 「장기적으로 개인정보
경로를 줄인다」를 여기서 실행했다 — 실제 인물 사진이 외부 모델로 나가지 않는다.
사진은 볼사람 private 스토리지에만 남아 프로필 사진으로 쓰인다.

딸려온 변경:

- `analyzeSession` 이 사진을 디스크에서 읽지 않는다(`readAsset`·`MAX_ANALYZE_IMAGES` 제거).
  그래서 **원문이 없으면 분석을 거부한다** — 사진만 있는 세션은 분석해도 전부 null 이다.
- 봇의 `/analyze` 도 원문이 있을 때만 동작한다.
- mock 프로바이더의 model 문자열이 `mock/3img` → `mock` 으로 바뀌었다.
- 가이드의 「AI 분석에는 앞쪽 6장까지」 정책이 사라졌다. 대신 「사진은 AI 에 보내지
  않는다」를 명시하고, `docs-guide.test.ts` 가 `ExtractionInput` 에 이미지 필드가
  없는지까지 검사한다.

아직 확인하지 않은 것: 텔레그램 **안에서** 앨범으로 보낼 때의 `media_group_id`
(안내 규칙이 더 이상 그 값에 의존하지 않으므로 동작에 영향 없음), HEIC 전송 시 mime,
webhook 재전송 간격, 20MB 초과 파일의 실패 형태.

## SMS 발송 계층 (2026-09-07 추가)

`apps/web/src/server/auth/login.ts` 의 마지막 TODO 를 정리했다. 코드가 없어서 막혀 있던
것이 아니라 **구조가 없어서** 막혀 있었다 — 발송 실패·미연동 상태가 `throw` 하나로
표현돼 있었고, 운영 배포로 가려면 인증 경로를 손봐야 했다.

AI 프로바이더와 같은 방식으로 추상화했다.

```
server/sms/
├── types.ts    SmsSender 인터페이스
├── console.ts  개발용 — 서버 로그에만 남긴다
└── index.ts    SMS_PROVIDER 로 선택
```

`SmsSender` 에 `delivers` 를 둔 것이 핵심이다. "보냈다"와 "사용자 휴대폰에 도착한다"는
다른 사실인데, 이걸 구분하지 않으면 콘솔 sender 가 운영에 올라가도 화면은 "인증번호를
보냈습니다"라고 말한다. 이제 `issueLoginCode` 가 `delivered` 를 함께 돌려주고,
로그인 화면은 도착하지 않는 경로일 때 주선자에게 문의하라고 안내한다.

**실제 업체 어댑터는 넣지 않았다.** 국내 발신번호 사전등록과 계약이 필요하고, 검증하지
않은 외부 API 를 추측으로 구현하지 않는다(카카오·텔레그램에서 같은 규칙을 적용했다).
업체가 정해지면 `SmsSender` 구현 한 파일과 `SMS_PROVIDER` 값 하나를 추가하면 된다.

`APP_ENV=production` + `SMS_PROVIDER=console` 조합은 기동을 막는다 — 문자가 도착하지
않는 배포에서는 회원이 로그인할 방법이 없으므로 조용히 깨지게 두지 않는다.

### 「기동을 거부한다」는 표현을 고쳤다

이 가드를 실제로 걸어보니 **프로세스가 죽지 않는다.** `instrumentation` 훅에서 던지면
Next 는 `Failed to prepare server` 를 남기고도 포트를 열고, 이후 **모든 요청이 500** 이
된다. 아무것도 서비스하지 않으므로 안전 목적은 달성되지만, `pm2 status` 에는 `online`
으로 보이므로 설정을 바꾼 뒤에는 상태가 아니라 기동 로그를 봐야 한다.
기존 `DEV_EXPOSE_OTP` 가드도 같은 방식이었고, 문서가 "기동을 거부한다"고 적어둔 것은
정확하지 않았다. `.ai-harness/project.md` 와 `env.ts` 주석을 실제 동작으로 고쳤다.

## 관리자 로그인 시도 제한 (2026-09-07 추가)

회원 OTP 에는 시도 제한(`login_codes.attempts`, 5회)이 있었지만 **관리자 비밀번호에는
아무 제한이 없었다.** 실측으로 확인했다 — 공개 도메인(`bolsaram.rheeeuro.com`)에
틀린 비밀번호를 10회 연속 보내도 전부 403 이고 차단이 없었다. 미들웨어도 없다.

실패를 행으로 남기고 "최근 15분 안의 실패 5회"로 판정한다(`admin_login_failures`).
카운터 컬럼 하나를 두는 대신 행으로 남긴 이유는 둘이다.

- 창이 지나면 자연히 풀려서 **영구 락아웃이 없다.** 주선자가 여러 명이 될 예정이라
  특정 계정을 무기한 잠글 수 있게 만들면 안 된다.
- 주선자가 공격 흔적을 볼 수 있다. 정리 작업이 14일 뒤 지운다.

판정은 **이메일 문자열 기준**이다. 존재하지 않는 이메일로 온 시도도 같이 세야
계정 존재 여부가 응답으로 드러나지 않는다. 비밀번호 검증(scrypt, N=16384)보다
앞에서 끊어 비싼 연산을 아낀다. 성공하면 창을 비운다 — 본인이 오타 몇 번 낸 뒤
맞췄으면 제한이 남지 않아야 한다.

IP 기준 제한은 넣지 않았다. cloudflared 뒤라 클라이언트 IP 를 헤더로 받아야 하고
그 헤더는 위조 가능하다 — 신뢰 경계를 정하지 않은 채 IP 로 판정하면 오히려
우회 수단이 된다. 필요해지면 프록시 신뢰 설정과 함께 추가한다.

### 남은 위험 — 시드 비밀번호

**시도 제한은 이미 알려진 비밀번호를 막지 못한다.** 확인 시점에 공개 도메인에서
시드 비밀번호(`bolsaram-admin`, 이 저장소에 문서화된 값)로 관리자 로그인이 되었다.
그 계정으로 전체 회원의 이름·연락처·프로필 원문·사진에 접근할 수 있다.
**비밀번호 교체가 시도 제한보다 우선이며, 자격 증명이라 사용자가 결정할 사항이다.**

### 함께 드러난 빈 자리 — 주선자 계정 추가 경로

주선자 계정을 만드는 경로가 `packages/db/src/cli/seed.ts` 의 INSERT 하나뿐이다.
회원가입 화면도, 관리자 초대 기능도 없다. 주선자가 여러 명이 될 예정이므로
SQL 을 직접 만지지 않고 추가할 방법이 필요하다. 아직 만들지 않았다.

## 모임(테넌트) 격리와 주선자 가입 (2026-09-07 추가)

「주선자를 위한 서비스니 주선자 가입을 열자」는 결정에서 출발했다. 그런데 당시 권한
모델은 그걸 견딜 수 없었다 — 관리자 정책이 전부 `app_is_admin()` 하나로만 판정해서
**ADMIN 계정 하나만 만들면 전체 회원의 이름·연락처·사진에 접근**할 수 있었다.
자유 가입을 그 위에 얹으면 누구나 가입해서 남의 회원 정보를 보게 된다.

그래서 순서를 잡았다 — **격리를 먼저 완성하고 가입을 나중에 붙였다.** 반대로 하면
그 사이에 구멍이 열린다.

### 정한 것 (사용자 결정)

| 축                    | 결정                                       |
| --------------------- | ------------------------------------------ |
| 모임당 주선자        | **여러 명** (`group_admins`, OWNER 한 명)  |
| 가입 인증            | 이메일 + 비밀번호                          |
| 가입 개방            | 자유 (초대 불필요)                         |

> 「회원 풀은 모임 안에서만」으로 시작했다가 **주선자와 모임을 분리**하는 쪽으로
> 바뀌었다. 아래 「전체공개 풀」 참고 — 그게 최종 모델이다.

모임 안에서만 보이게 한 이유는 「주선자가 검증한 사람만」이라는 제품 원칙과 맞고,
모임을 넘는 연결을 누가 책임지느냐는 문제가 생기지 않기 때문이다.

### 구현 (`0010_groups.sql`)

`groups` · `group_admins` 를 넣고 `profiles.group_id` · `import_sessions.group_id` 를
NOT NULL 로 조였다. 기존 데이터는 「기본 모임」으로 이관했다(주선자 1명·프로필 26건).

판정은 GUC 를 새로 만들지 않고 **SECURITY DEFINER 함수가 `group_admins` 를 직접
조회**한다 — 애플리케이션이 자기 그룹을 스스로 주장할 수 없게 하려는 것이다.

| 함수                          | 판정                               |
| ----------------------------- | ---------------------------------- |
| `app_is_group_admin(uuid)`    | 현재 사용자가 그 모임의 주선자인가 |
| `app_current_member_group()`  | 현재 회원이 속한 모임              |
| `app_can_admin_profile(uuid)` | 그 프로필 모임의 주선자인가        |

정책 15개를 다시 썼다. 함께 좁힌 것 — 회원 Discover(자기 모임만), 모임을 넘는 소개
신청(DB 차단), 텔레그램 연결(주선자 개인 것, 같은 모임에도 비공개), `users` 조회
(관리자가 남의 계정을 임의로 못 봄), `audit_logs`(본인 기록만).

### 가입 (`server/auth/signup.ts`)

계정과 모임을 **한 트랜잭션으로** 만든다. 계정만 생기고 모임이 없으면 로그인은 되는데
아무것도 못 하는 상태가 남는다. 이메일 중복으로 실패하면 모임도 만들어지지 않는지
테스트로 고정했다.

가입 비밀번호는 10자 이상이다(로그인은 기존 계정을 받아야 하므로 8 유지). 이 계정
하나로 모임 전체 회원의 개인정보에 접근하므로 새 계정에는 더 강한 기준을 적용했다.

모임에서 제거된 주선자를 위해 `POST /api/admin/groups` 를 두었다. 관리자 대시보드가
모임이 없으면 KPI 대신 「모임 만들기」 안내를 보여준다 — RLS 가 전부 막아 0 으로만
보이는 화면 대신 이유를 알려준다.

### 이 과정에서 잡은 버그

`commitSession` 이 프로필을 만들 때 `group_id` 를 넣지 않아 **등록 자체가 깨졌다**
(NOT NULL 위반). 커밋하는 주선자의 모임이 아니라 **Import 세션의 모임**을 쓰도록 했다 —
세션을 볼 수 있다는 것 자체가 RLS 로 그 모임 주선자임을 뜻하고, 여러 모임에 속한
주선자가 엉뚱한 모임에 등록하는 일을 막는다.

`tests/admin-login.test.ts` 에 실행 간 간섭이 있었다. 존재하지 않는 이메일로 쌓은
실패 기록이 남아 다음 실행을 RATE_LIMITED 로 만들었다. TAG 기반 고유 주소로 바꿨다.

### 검증

`tests/group-isolation.test.ts` 11개와 `tests/admin-signup.test.ts` 7개를 추가했다.
전부 "안 되는 것"을 검사한다 — 남의 모임 읽기·쓰기·초대·Import, 모임을 넘는 신청,
그리고 **가입만으로는 아무것도 볼 수 없다**. 기존 `rls.test.ts` 22개도 그대로 통과한다.

실제로 띄워 확인했다 — 방금 가입한 계정에게 기존 모임의 Import 4건이 보이지 않고,
기존 주선자에게는 그대로 4건이 보인다.

### 아직 안 한 것

**동료 주선자 초대.** 지금은 각자 가입하면 각자 모임이 생겨서 같은 모임에서 함께
일할 방법이 없다. 텔레그램 연결 코드와 같은 방식(해시 저장·짧은 만료·1회용)으로
모임 초대 코드를 만들고, 가입 시 코드가 있으면 새 모임을 만들지 않고 그 모임에
합류하게 하는 것이 다음 단계다.

→ 0012 에서 그대로 만들었다(「전체공개 풀」의 「가입 / 모임 만들기 / 모임 참여」).
가입 폼에 코드 칸을 붙이는 대신 가입 뒤 `/admin/group` 에서 참여하는 형태가 됐다.

## 전체공개 풀 — 주선자와 모임 분리 (2026-09-07 재설계)

0010 은 모든 프로필을 모임에 강제로 넣고 가입 시 모임을 자동 생성했다. 그래서
갓 가입한 주선자는 **빈 화면**만 봤다. 「주선자와 모임은 따로 가야 한다」는 결정으로
모델을 바꿨다.

**소속 여부가 곧 공개 여부다.**

```
group_id IS NULL      → 전체공개. 모든 주선자가 본다.
group_id IS NOT NULL  → 그 모임 주선자만 본다.
```

공개 여부를 별도 컬럼으로 두지 않았다 — 두 축으로 나누면 「모임 소속인데 전체공개」
같은 모순 상태가 생긴다. 소속이 없다는 것이 곧 공개라는 뜻이다.

### 읽기와 쓰기를 다르게 준다

전체공개 프로필을 **누구나 볼 수 있게** 하면서 **아무나 고칠 수 있게** 하면 안 된다.
그래서 판정을 둘로 갈랐다.

| 함수                                  | 판정                                            |
| ------------------------------------- | ----------------------------------------------- |
| `app_can_view_profile_as_admin(uuid)` | 전체공개이거나 자기 모임 (읽기)                 |
| `app_can_edit_profile(uuid)`          | 자기 모임이거나, 전체공개인데 **자기가 등록**   |
| `app_can_edit_import(uuid)`           | 위와 같은 판정을 Import 세션에                  |

회원 풀 판정은 `IS NOT DISTINCT FROM` 을 쓴다 — 전체공개 회원끼리도 서로 보이고
(둘 다 NULL), 풀을 넘는 소개 신청은 DB 에서 막힌다.

### 가입 / 모임 만들기 / 모임 참여

가입(`POST /api/auth/signup`)은 **계정만** 만든다. 모임은 그 뒤 선택이다.

- 만들기 — `POST /api/admin/groups`
- 참여 — `PUT /api/admin/group` + 초대 코드
- 초대 코드 발급 — `POST /api/admin/group` (모임에 속한 주선자만)

초대 코드는 `invites`·`telegram_link_codes` 와 같은 방식이다(해시 저장·24시간·1회용·
조건부 UPDATE 로 replay 차단). 한 사람은 한 모임에만 속한다 — 모임 전환 UI 가 없어
여러 모임에 속하면 어디서 일하는지 헷갈린다.

### 이 과정에서 잡은 취약점 — `profiles_claim`

테스트가 예상과 다른 실패(0건이 아니라 RLS 예외)를 낸 덕에 발견했다.
`profiles_claim` 정책이 이렇게 열려 있었다.

```sql
USING (user_id IS NULL AND app_current_user_id() IS NOT NULL)
WITH CHECK (user_id = app_current_user_id())
```

**아무 로그인 사용자나 주인 없는 프로필을 자기 것으로 만들 수 있었다** — 초대 토큰도,
모임 소속도 보지 않는다. 0006 부터 있었고 0010 이 「모임은 초대가 정한다」는 주석과
함께 그대로 뒀는데, 실제로는 초대를 확인하지 않았다.

그런데 앱의 실제 claim 경로(`claimInvite`)는 owner 커넥션을 쓰므로 RLS 를 우회한다 —
**이 정책은 어느 코드에도 쓰이지 않았다.** 얻는 것 없이 열려 있었던 셈이다.
HTTP 로 그 UPDATE 를 내보내는 경로는 없어 즉시 악용은 불가능했지만, 「RLS 와 앱
레이어에 중복으로 둔다」는 원칙에서 RLS 쪽이 비어 있었다.

0013 에서 정책을 제거했다. 정상 claim(초대 토큰 → owner 경로)은 그대로 동작함을
확인했고, `group-isolation.test.ts` 에 가로채기 차단 케이스를 넣었다.

### 검증

`tests/admin-signup.test.ts` 를 새 모델로 다시 썼다(13개) — 가입이 모임을 만들지
않는지, 전체공개가 보이는지, 모임 소속은 안 보이는지, **전체공개를 남이 고칠 수
없는지**, 초대 코드 재사용·만료·중복 소속 차단, 합류자가 개설자가 아닌지.

실제로 띄워 확인했다 — A 가입(모임 없음) → 모임 생성 → 초대 코드 발급 →
B 가입 → 코드로 합류 → 같은 모임에 주선자 2명(개설자/참여). 전체 265개 통과.

### 남은 것

- **전체공개 풀이 비어 있다.** 이 호스트의 시드 프로필 26건이 0010 마이그레이션 때
  「기본 모임」으로 들어갔다. 시드 코드는 이제 `group_id` 없이(=전체공개) 만들므로
  새로 설치하면 전체공개로 생긴다. 기존 26건을 전체공개로 옮길지는 운영 판단이다.
- **모임 나가기**가 없다. 다른 모임으로 옮기려면 SQL 이 필요하다.
- 신선한 설치에서 0010 의 DO 블록이 주선자 없는 「기본 모임」을 하나 남긴다(무해하지만
  군더더기).

## 모임 설정 화면 (2026-09-07 추가)

모임에 `name` 하나만 있었고, **만든 뒤 바꿀 방법이 없었다.** `groups_owner_update`
정책은 0010 에서 만들어뒀는데 엔드포인트도 화면도 없어서 정책만 깔고 쓰지 않은 상태였다.

- `groups.description` 추가(500자, 0014). **주선자끼리 보는 메모**이고 회원에게는
  노출하지 않는다. 초대받은 사람이 맞는 모임인지 판단할 근거가 필요했다.
- `PATCH /api/admin/group` — 보낸 필드만 바꾼다. 설명에 빈 문자열을 보내면 지운다
  (`CASE WHEN btrim($3) = '' THEN NULL`).
- `/admin/group` 전용 화면 신설. 모임이 없으면 만들기·참여, 있으면 정보 수정·주선자
  목록·초대 코드 발급을 한곳에 모았다. 관리자 네비에 「모임」 메뉴를 더해 여섯 개가 됐다.
- 대시보드의 모임 칸은 없애고 빠른 작업 링크로 바꿨다 — 설정은 전용 화면에 모은다.

수정 권한은 **같은 모임 주선자 누구나**로 뒀다. 개설자만으로 좁히면 개설자가 계정을
지웠을 때 아무도 못 고친다. RLS(`groups_owner_update`)도 같은 판정이다.

실제로 확인했다 — 가입 → `/admin/group` 200 → 이름·설명으로 모임 생성 → 조회 →
이름·설명 수정까지 동작한다. 테스트 5개를 더해 271개 통과.

## 모임 나가기 · 시드 프로필 이관 · 비밀번호 교체 (2026-09-07)

**시드 프로필 26건을 전체공개로 옮겼다.** 0010 마이그레이션이 기존 프로필을 전부
「기본 모임」에 넣어서 새로 가입한 주선자가 빈 목록을 봤다. 합성 시드 데이터이고
시드 코드도 이제 `group_id` 없이(=전체공개) 만들므로 코드와 데이터를 맞춘 것이다.
**텔레그램으로 올린 Import 4건은 실제 인물이라 모임에 남겼다.**

**모임 나가기(`DELETE /api/admin/group`)를 만들었다.** 막는 경우가 하나 있다 —
마지막 주선자인데 모임에 회원이나 Import 가 남아 있으면 나갈 수 없다. 나가면 그
데이터를 아무도 볼 수 없게 되고(RLS 가 전부 막는다) 되돌릴 방법이 없다.

- 빈 모임이면 나가면서 모임까지 지운다 — 주인 없는 빈 모임을 남기지 않는다.
- 개설자가 나가고 다른 주선자가 남으면 가장 먼저 들어온 사람에게 개설자를 넘긴다.
  `group_admins_one_owner` 때문에 개설자 없는 모임을 만들 수 없다.

**시드 비밀번호를 교체했다.** `bolsaram-admin` 은 이 저장소에 문서화된 값이고 공개
도메인(`bolsaram.rheeeuro.com`)에서 통했다. 주선자 가입이 열린 뒤로는 「기본 모임」의
데이터를 쥔 계정이 더 눈에 띄는 표적이 된다. 임의 값으로 바꾸고 확인했다 —
기존 값 403, 새 값 200.

`pnpm db:seed` 는 여전히 문서화된 기본값을 쓴다. 새로 시드한 환경을 공개 주소에
붙이면 같은 문제가 생긴다는 점을 `.ai-harness/project.md` 에 적어뒀다.

## 회원 로그인을 매직 링크로 (2026-09-07)

SMS 를 쓰지 않기로 했다. 회원 로그인 경로가 전화번호 OTP 하나였고 발송 수단이 없어
실제로 동작할 수 없었다. 그리고 확인해 보니 **회원 계정을 만드는 경로가 시드밖에
없었다** — `verifyLoginCode` 는 기존 계정만 찾고 없으면 「초대된 번호가 아닙니다」로
거부했다. 즉 실제 회원을 받을 방법이 애초에 없었다.

주선자가 이미 카카오톡으로 초대 링크를 보내고 있다. 그 링크가 세션까지 만들면 별도
발송 수단이 필요 없고, 소비할 때 계정도 함께 만들 수 있다.

```
초대 링크 소비 (consumeInvite)
  프로필에 주인이 없으면 → 회원 계정 생성 + 연결 + 세션   (firstTime)
  주인이 있으면        → 그 계정으로 세션                 (재로그인)
```

`/api/claim` 은 **로그인을 요구하지 않는다** — 이 경로가 로그인이다. 세션(30일)이
만료되면 주선자가 링크를 재발급한다. 링크를 가진 사람이 곧 그 회원이 되므로 1회용·
72시간이며, 주선자가 본인에게 직접 전달하는 것이 전제다.

전화번호는 더 이상 신원이 아니다. `users_member_needs_phone` 제약을 없애고(0015)
주선자가 기록하는 연락 수단으로만 남겼다.

### 지운 것

`login_codes` 테이블, `server/sms/`, `/api/auth/otp/*`, 로그인 화면의 회원 탭,
`DEV_EXPOSE_OTP`·`SMS_PROVIDER` 환경변수, `isLoopbackDeployment()`,
정리 작업의 로그인 코드 단계. **안 쓰는 인증 경로를 남겨두는 것 자체가 공격면이다.**

`docs-guide.test.ts` 의 OTP 정책 검사(5분·30초·5회)를 「회원 로그인에 인증번호를
쓰지 않는다」로 바꿨다 — `login.ts` 에 OTP 함수·상수가 없는지 본다(주석은 정당한
설명이므로 심볼만 검사한다).

### 이 과정에서 잡은 스키마 버그

정리 중에 회원 계정 DELETE 가 실패했다. `invites.claimed_by` 는 `ON DELETE SET NULL`
인데 `invites_claim_pair` 가 `claimed_at` 과 짝을 요구했다 — FK 가 NULL 로 바꾸려
하면 제약에 걸린다. **즉 링크를 쓴 회원을 삭제할 수 없었다.** 탈퇴 처리가 막히는 셈이다.

0004 부터 있던 문제이고 매직 링크로 회원 계정이 만들어지기 시작한 뒤로 더 자주
부딪힌다. 제약을 한 방향만 남기도록 완화했다(0016) —
`claimed_by IS NULL OR claimed_at IS NOT NULL`. replay 를 막는 것은 `claimed_at` 이고
`claimed_by` 는 계정이 사라지면 잃을 수 있는 감사 정보다.

구현에서도 순서를 바꿨다. 처음에는 `claimed_at` 만 먼저 쓰다가 같은 제약에 걸렸다 —
**누구로 소비할지 정한 뒤 한 번에** 써야 한다. 행을 `FOR UPDATE` 로 잠가 동시 요청을
직렬화하고, UPDATE 에 `claimed_at IS NULL` 조건을 한 번 더 둔다.

### 검증

`tests/member-magic-link.test.ts` 8개 — 링크 하나로 계정 생성·연결, 재사용 차단,
만료·회수 차단, 재발급 시 이전 링크 무효, 재로그인이 계정을 새로 만들지 않음,
미리보기가 상태를 바꾸지 않음, **링크를 쓴 회원을 삭제할 수 있음**.

실제로 띄워 확인했다 — 초대 발급 → 링크로 최초 로그인(firstTime true) → `/discover`
200, 전체공개 21건 탐색 → 같은 링크 재사용 거부 → 링크 재발급으로 재로그인
(firstTime false, 계정 재생성 없음). 전체 280개 통과.

### 남은 것

세션 만료마다 주선자 손이 간다. 그게 이 방식의 비용이고, 사용자가 알고 고른 것이다.
회원 스스로 재로그인할 방법이 필요해지면 그때 이메일이나 비밀번호를 붙인다.

## 운영 전환과 개인정보 처리방침 (2026-09-07)

### APP_ENV=production

뒤집기 전에 확인해 보니 **`APP_ENV` 에 아무것도 걸려 있지 않았다.** 유일한 소비자였던
`DEV_EXPOSE_OTP` 게이트가 매직 링크 전환으로 사라졌고, `isLiveDeployment()` 는
export 만 되어 있고 아무도 쓰지 않았다. 그냥 뒤집으면 기동 로그 문자열만 바뀐다.

그래서 production 이 실제로 무언가를 지키게 만들었다.

- **`APP_ORIGIN` 이 https 여야 한다.** 초대 링크와 봇 검토 버튼이 이 주소로 나간다.
  loopback 이면 회원에게 보낸 링크가 열리지 않는다 — 이 호스트에서 실제로 겪었다.
- **`.env.example` 의 기본 시크릿(`change-me…`)을 쓸 수 없다.**

미사용 export `isLiveDeployment()` 는 지웠다.

`pnpm deploy:web`(= `pm2 restart bolsaram-web`)은 **ecosystem 의 env 를 다시 읽지
않는다.** 기동 시점 값을 재사용하므로 `APP_ENV` 를 바꾼 뒤에는
`pm2 restart ecosystem.config.cjs --only bolsaram-web --update-env` 가 필요하다.
(다른 프로젝트 앱을 건드리지 않도록 `--only` 를 반드시 붙인다.)

가드가 실제로 막는지 확인했다 — `APP_ORIGIN=http://…` 로 띄우면 기동 훅이 던지고
모든 요청이 500 이 된다.

### 개인정보 처리방침

`docs/guide/privacy.md` 를 썼다. 템플릿이 아니라 **코드에서 뽑은 사실**로 채웠다 —
저장 컬럼, `RETENTION` 상수, 외부로 나가는 경로, RLS·signed URL·해시 저장.

`tests/docs-guide.test.ts` 가 정합성을 고정한다. 보관 기간 5개가 `cleanup.ts` 의 값과
같은지, 「사진을 AI 에 보내지 않는다」·「연결 전 이름·연락처 비공개」·「전체공개는 모든
주선자가 본다」가 적혀 있는지 검사한다. 방침에 적은 숫자가 코드와 어긋나면 실패한다.

방침이 주장하는 것을 공개 도메인에서 실제로 확인했다 —
`x-robots-tag: noindex…`, 서명 없는 사진 접근 401, 비로그인 프로필 조회 401.

**법률 검토를 받지 않았다.** 문서 맨 위에 그렇게 적었고, 두 가지를 「짚어야 할 것」으로
남겨 뒀다.

1. **등록되는 사람의 동의.** 프로필은 주선자가 대신 등록하므로 그 시점에 본인이
   볼사람을 모를 수 있다. 전체공개로 등록하면 가입한 모든 주선자가 본다는 사실까지
   알려야 하는데, 동의를 어떻게 받고 어디에 남길지가 정해져 있지 않다.
2. **개인정보 보호책임자·문의 창구·사업자 정보**가 비어 있다.

둘 다 코드로 풀 문제가 아니라 운영 방식을 정하는 문제다.

## 시크릿 재발급 (2026-09-07)

작업 기록에 남은 값을 전부 교체했다. 실사용자가 0명일 때가 가장 싸다 —
회원이 생긴 뒤에는 같은 교체가 훨씬 비싸다.

| 대상                  | 교체 주체 | 영향                                   |
| --------------------- | --------- | -------------------------------------- |
| 텔레그램 봇 토큰      | 사용자    | **webhook 등록이 함께 풀린다** — 재등록 필요 |
| OpenAI 키             | 사용자    | 없음                                   |
| `SESSION_SECRET`      | 여기서    | 전원 로그아웃                          |
| `STORAGE_SECRET`      | 여기서    | 열려 있던 사진 URL 만료                |
| `INVITE_TOKEN_PEPPER` | 여기서    | 발급된 링크·코드 전부 무효             |

pepper 를 바꾸면 `token_hash` 가 옛 값으로 계산돼 있어 **어떤 링크도 통하지 않는다.**
방치하면 「왜 안 되지」가 되므로 상태를 실제와 맞췄다 — 세션 28건 회수,
미소비 초대 회수, 봇 연결 코드·모임 초대 코드 삭제.

영향 없는 것도 확인했다. 주선자 비밀번호는 scrypt(자체 salt)라 무관하고,
`telegram_connections` 는 해시가 아니라 매핑이므로 유지된다.

교체 후 전 경로를 확인했다 — 주선자 로그인 200, 새 세션 쿠키로 `/admin` 200,
새 pepper 로 초대 발급 → 링크 로그인(firstTime true), 새 `STORAGE_SECRET` 으로
서명한 사진 열기 200(훼손 서명은 거부).

### 시크릿을 대화에 노출하지 않는 경로

값을 알려주려면 어딘가에 적어야 하고 그 순간 다시 노출된다. 그래서 **토큰이 사람 손을
거치지 않고 확인·등록되는 스크립트**를 만들었다.

```bash
pnpm ai:check                  # OpenAI 키·모델 사용 가능 여부
pnpm telegram:webhook          # 봇 이름·등록 주소·보류 update
pnpm telegram:webhook --set    # APP_ORIGIN 기준으로 재등록
```

둘 다 값을 출력하지 않는다. 실패해도 토큰이 든 URL 을 찍지 않고, 키는 길이만 보여준다
(안 읽힌 건지 틀린 건지 가르기 위해서다).

만드는 과정에서 **앞서 앱에만 넣었던 Happy Eyeballs 보정이 스크립트에는 없어서**
텔레그램 호출이 실패했다. `setDefaultAutoSelectFamilyAttemptTimeout(2000)` 을 같이 넣었다.

## 주선자 알림 · 백업 · 등록 동의 (2026-09-08)

돌아가는 서비스에 빠져 있던 세 가지를 채웠다. 셋 다 새 기능이라기보다,
**실제 사람이 쓰기 시작하면 그날 문제가 되는 것들**이다.

### 아무도 알림을 받지 않고 있었다

신청 생성은 감사 로그만 남겼다. 회원은 로그인해야 알고(세션이 만료되면 주선자가 링크를
다시 보내야 한다), 주선자는 `/admin/requests` 를 열어봐야 안다. 수락된 건은 주선자가
연결해 주지 않으면 거기서 멈추므로 — **주선자가 모르면 플로우 전체가 멈춘다.**

요청 경로에서 텔레그램을 직접 호출할 수는 없었다. 회원의 RLS 컨텍스트에서는 담당
주선자가 누구인지도, 그 사람의 텔레그램 연결도 읽을 수 없다(정책이 없다). owner
커넥션을 요청 경로에서 쓰는 것은 이 저장소의 규칙이 금지한다.

그래서 아웃박스로 갈랐다(0017).

```
회원 트랜잭션 → 트리거(SECURITY DEFINER)가 notifications 에 행 추가
             → scheduleDispatch()  응답을 기다리지 않는다
디스패처      → attempts+1 로 선점 → 텔레그램 → sent_at
```

부수 효과가 아니라 이득이었다. 텔레그램이 느려도 「마음 보내기」가 느려지지 않고,
전이가 **실제로 성공했을 때만** 알림이 생기므로(조건부 UPDATE 가 0행이면 트리거도
안 돈다) 애플리케이션이 알림을 빠뜨리는 실수가 구조적으로 불가능하다.

payload 에는 **공개 번호만** 넣는다. 그래서 발송 시점에 프로필을 다시 읽을 필요가 없고,
디스패처가 owner 로 만지는 범위가 `notifications` 와 `telegram_connections` 로 좁아진다.

**0018 이 필요했던 이유.** 0017 은 `GRANT SELECT` 만 줬는데 0001 의
`ALTER DEFAULT PRIVILEGES` 가 새 테이블에 DML 을 자동으로 준다(0009 가 같은 이유로
회수했다). 정책이 없어 실제로는 0행이 바뀌고 **오류도 나지 않아 통과한 것처럼 보였다** —
테스트가 그걸 잡았다. 정책 하나만 잘못 추가하면 열리므로 권한 자체를 회수했다.

실제로 띄워 확인했다 — 신청 행 하나를 만들고 앱을 재시작하니 기동 스윕이 집어
텔레그램으로 나갔고 `sent_at` 이 찍혔다.

### 백업이 없었다

`pg_dump` 가 리포 어디에도 없었다. cron 은 **지우는 쪽**(cleanup) 하나뿐이었다.

`scripts/db-backup.sh` + PM2 `bolsaram-backup`(매일 03:40). 정리(04:10)보다 **먼저**
돌린다 — 정리가 지운 것도 하루치 백업에는 남아 있어야 실수를 되돌릴 수 있다.

「백업이 있다」와 「되살릴 수 있다」는 다른 말이라서 `--verify` 를 함께 만들었다.
최근 덤프를 임시 DB 로 복구해 행 수를 세고 지운다. 실제로 돌려 26건이 돌아오는 것을
확인했다. 매 백업 직후에도 `pg_restore --list` 로 형태를 확인한다 — 잘린 덤프는
파일이 있는 것처럼 보여서 더 위험하다.

덤프에는 실명·연락처가 들어 있어 가드에 백업 디렉터리를 추가했다. 이때 가드의 구멍이
드러났다 — 읽기 금지 판정이 **알려진 읽기 명령 목록**에 걸려 있어서 `pg_restore` 같은
목록 밖 도구로 덤프를 열면 그냥 통과했다. 도구를 쫓아다니는 대신 경로를 기준으로
바꿨다: 개인정보 디렉터리는 어떤 명령의 인자로 나와도 막는다.

### 동의를 기록할 자리가 없었다

처리방침이 「짚어야 할 것」으로 남겨 둔 항목이다. 프로필은 주선자가 남을 대신해
등록하므로 그 시점에 본인은 볼사람을 모를 수 있고, 전체공개면 가입한 모든 주선자가 본다.

동의를 **어떻게** 받을지는 운영이 정할 문제라 손대지 않았다. 대신 **받았다는 사실을
남길 자리**를 만들고(0019), 기록 없이는 게시되지 않게 했다.

기존 행을 어떻게 채울지가 유일하게 어려운 결정이었다. 「동의받았다」로 채우면 받은 적
없는 동의가 기록으로 남고, 전부 내리면 돌고 있는 서비스가 멈춘다. 그래서 두 표식을
두고 갈랐다 — Import 로 등록된 것(실제 사람일 수 있다)은 `LEGACY`(확인 필요),
나머지는 시드가 만든 `SYNTHETIC`.

그래서 게이트가 두 겹이다.

| 어디    | 무엇을 막는가                                         |
| ------- | ----------------------------------------------------- |
| DB 제약 | 기록이 **아예 없는** 프로필의 게시                    |
| 도메인  | 실제 확인이 아닌 표식(SYNTHETIC·LEGACY)으로의 새 공개 |

이미 게시된 LEGACY 프로필은 그대로 두되, **공개 범위를 다시 손대는 순간** 실제 방법을
기록해야 한다. 비공개로 내리는 것은 기록과 무관하게 언제나 된다 — 문제를 발견하면
먼저 내릴 수 있어야 한다.

`SYNTHETIC` 표식은 정리 도구의 근거가 되기도 한다. `pnpm db:purge-seed` 는 이름이나
날짜를 추측하지 않고 이 값만 보고 걷어낸다. 이 호스트에서 미리보기를 돌리면 합성
프로필 24건·사진 48장·회원 계정 7개가 잡히고, 실제 삭제는 사용자 판단으로 남겼다.

### 함께 정리한 문서 드리프트

읽다가 발견한 것들이다. 루트 README 가 `APP_ENV=staging` 과 `DEV_EXPOSE_OTP` 를
안내하고 있었고(매직 링크 전환으로 사라진 값), 「SMS 미연동」·「배포 구성 없음」이
남아 있었으며, 테스트 개수가 171 개로 적혀 있었다. `crypto.ts` 의 `generateOtp()` 는
아무도 부르지 않는 채로 남아 있어 지웠다.

### 이어서 정리한 것 (2026-09-08)

**회원 알림은 만들지 않기로 했다.** 주선자만 텔레그램으로 받고, 회원은 시그널 화면에서
직접 확인한다. 연락이 필요한 일은 주선자가 카카오톡으로 한다. 「채널이 없다(구멍)」가
아니라 **결정**이므로 문서를 그 축으로 고쳤고, FAQ 에 「알림이 오나요」 항목을 넣었다.

**동의 확인이 필요한 프로필을 화면이 드러내게 했다.** 기록할 자리만 만들어 두면 아무도
찾아가지 않는다.

- 대시보드 맨 위에 건수 — **그중 회원에게 보이고 있는 것이 몇 건인지** 함께 보여준다.
  기록이 없는데 공개돼 있는 상태가 제일 급하기 때문이다.
- 프로필 목록의 「동의 확인 필요」 뱃지와 필터(`?consent=pending`).
- 합성 데이터(SYNTHETIC)는 이 집계에서 뺐다 — 확인할 대상이 아니라 지울 대상이다.

**백업 사본 위치를 설정으로 열었다.** `BACKUP_MIRROR_DIR` 을 주면 백업이 성공한 뒤에만
다른 디스크·마운트로 복사하고 거기서도 같은 개수만 남긴다. 경로를 못 쓰면 **경고만 하고
기본 백업은 유지한다** — 마운트가 빠졌다고 백업 자체를 잃으면 안 된다. 실제로 경로가
없는 경우까지 돌려 확인했다. 환경변수는 리포 루트 한 파일로 관리하는 규칙이라
셸 스크립트가 그 값을 직접 꺼내 쓴다(웹 앱과 달리 자동으로 읽히지 않는다).

원격 저장소로 보내는 경로는 여전히 없다. 이건 어디로 보낼지가 정해져야 하는 문제다.

### 하지 않은 것과 그 이유

**동의 기록이 없는 프로필 2건을 비공개로 내리지 못했다.** DB 를 직접 고치는 것은 이
환경의 권한 정책이 막고, 주선자 비밀번호가 교체돼 있어 화면으로도 할 수 없었다.
관리자 화면 → 프로필 → 해당 건 → 노출을 **비공개**로 바꾸면 된다. 새 도메인 게이트가
있으므로 다시 공개하려면 그때 동의를 기록하게 된다.

**시드 데이터는 지우지 않았다.** 지금 지우면 둘러볼 프로필이 사실상 사라져 개발·시연이
막힌다. 실회원을 받기 시작할 때 `pnpm db:purge-seed --yes` 로 걷어내는 것이 맞다.

### 등록 동의 기록을 되돌렸다 (2026-09-08)

만든 당일에 뺐다. 판단은 **주선자가 동의를 받은 프로필만 올린다고 전제한다**는 것이다.
시스템이 그 사실을 다시 받아 적게 만들면 일만 늘고, 기록이 있다는 것이 동의를 받았다는
보장도 아니다.

0020 이 0019 를 되돌린다 — 컬럼 네 개, 제약 세 개, 인덱스, enum, 게시 게이트, 관리자
화면의 기록 칸·목록 뱃지·필터·대시보드 배너, 그리고 도메인 판정과 테스트까지.

**한 가지만 남겼다.** 0019 의 `SYNTHETIC` 은 동의 기록이면서 동시에 「이건 합성
데이터다」라는 표식이었고, `pnpm db:purge-seed` 가 그 값으로 시드를 가려낸다.
그 용도만 `profiles.is_seed` 불리언으로 옮겼다. 동의와 무관한 축이라 애초에 이쪽이
맞는 자리였다.

되돌리면서 **처리방침의 약속도 함께 되돌렸다.** 「기록이 없으면 공개할 수 없습니다」가
더는 사실이 아니기 때문이다. 지금 방침은 동의를 받는 것이 주선자 책임이라고 밝히고,
고지 문구와 철회 절차는 정해지지 않았다고 남겨 둔다. 문서가 코드보다 많은 것을
약속하지 않게 하는 것이 이 저장소가 테스트로 고정해 온 성질이다.

## 도메인 교체 — bolsaram.com (2026-09-08)

`bolsaram.rheeeuro.com` 에서 구매한 `bolsaram.com` 으로 옮겼다. 개인 도메인의 서브
도메인이 아니라 서비스 이름 그대로의 주소를 쓰는 편이 초대 링크를 카카오톡으로 받는
회원에게 덜 수상하다. 구 주소는 남기지 않고 완전히 교체했다.

바꿔야 하는 곳이 세 군데다 — **셋 중 하나만 어긋나도 조용히 깨진다.**

| 대상                                | 무엇이 걸려 있나                                 |
| ----------------------------------- | ------------------------------------------------ |
| `.env` 의 `APP_ORIGIN`              | 초대 링크(`/claim/<token>`), 봇 검토 버튼 URL     |
| Cloudflare Tunnel ingress           | 새 호스트가 `localhost:3020` 으로 들어오는 경로   |
| 텔레그램 `setWebhook`               | 봇 업데이트가 도달하는 주소                       |

`APP_ORIGIN` 을 바꿔도 **`pm2 restart` 만으로는 반영되지 않는다.** `pnpm deploy:web`
은 기동 시점 env 를 재사용하므로
`pm2 restart ecosystem.config.cjs --only bolsaram-web --update-env` 가 필요하다
(「운영 전환과 개인정보 처리방침」에 같은 함정을 적어 뒀다).

webhook 은 자동으로 따라오지 않는다. 도메인을 바꾼 뒤 `pnpm telegram:webhook --set`
을 돌려 새 `APP_ORIGIN` 기준으로 다시 등록해야 하고, `pnpm telegram:webhook` 으로
등록 주소를 확인한다.

**이미 나간 초대 링크는 전부 죽는다.** 토큰 자체는 유효하지만 링크에 박힌 호스트가
사라지기 때문이다. 세션(30일)은 쿠키 도메인이 달라 함께 끊긴다 — 회원은 주선자가
새 주소로 링크를 다시 보내야 들어올 수 있다. 실사용자가 적을 때 옮기는 이유다.

이력으로 남은 옛 도메인 언급(실기기 검증·로그인 시도 제한·시드 비밀번호 교체)은
그때 실제로 그 주소에서 확인한 사실이므로 고치지 않았다.

## 수락이 곧 연결 — 주선자 연결 게이트 제거 (2026-09-08)

설계문서 §4 의 상태 기계는 `REQUESTED → ACCEPTED → INTRODUCED` 였다. 상대가 수락한
뒤에도 주선자가 `/admin/requests` 에서 **연결하기** 를 눌러야 이름과 연락처가 열렸다.
0021 에서 그 중간 단계를 없앴다 — `accept` 가 바로 `INTRODUCED` 로 간다.

### 왜 뺐나

게이트가 지키려던 것은 **동의 없이 연락처가 오가지 않는 것**이었다. 그런데 그 동의는
수락 그 자체다. 주선자가 한 번 더 승인해서 새로 검증되는 사실이 없었고, 대신
**아무도 누르지 않으면 두 사람이 무한정 대기하는 단일 실패점**이 됐다. 회원에게는
알림을 보내지 않기로 했으므로(「회원 알림」) 대기 중인 쪽은 이유도 알 수 없었다.

주선자가 실제로 하는 일 — 두 사람에게 연락해 자리를 만드는 것 — 은 시스템 밖에 있다.
그 일은 알림으로 알려주면 되고, 상태를 붙잡아 둘 필요가 없다.

### 남긴 것

| 것                        | 어떻게                                                          |
| ------------------------- | --------------------------------------------------------------- |
| `MATCH_ACCEPTED` 알림     | 유지. 문구만 「연결해 주세요」→「연결됐습니다」                  |
| `introduce_note` 컬럼     | 읽기 전용. 회원 시그널 화면이 계속 표시하고 새로 쓰는 경로는 없음 |
| 관리자 `close`            | 유지. 마무리는 여전히 사람이 판단한다                           |
| enum 값 `'ACCEPTED'`      | DB 에 남는다. Postgres 는 enum 값 제거를 지원하지 않는다        |

`introduce_note` 를 남긴 이유는 회원이 주선자의 말을 보는 **유일한 창구**이기 때문이다.
연결된 건에 사후 메모를 남기는 UI 가 필요해지면 그때 붙인다. 그전까지 시드가 이 표시
경로를 살려 둔다.

### 마이그레이션 순서에 걸린 함정

0021 은 남아 있던 `ACCEPTED` 행을 `INTRODUCED` 로 올린다. 이 UPDATE 를 **알림 트리거
함수를 갈아끼우기 전에** 해야 한다. 새 함수는 `INTRODUCED` 진입을 알림 사건으로 보므로,
순서를 바꾸면 과거 건 전부에 대해 주선자에게 알림이 쏟아진다. 옛 함수는 `INTRODUCED` 를
무시하기 때문에 backfill 을 먼저 두면 트리거를 끄지 않고도 조용히 지나간다.

`match_requests_stamp` 도 함께 고쳤다. 수락이 곧 연결이라 `INTRODUCED` 에서
`responded_at` 과 `introduced_at` 을 함께 찍는다(이미 찍혀 있으면 덮어쓰지 않는다).

### 딸려 나온 두 가지

**종료가 공개를 회수하고 있었다.** `introducedPartnerIds` 와 RLS 의
`app_is_introduced_with` 가 둘 다 `status = 'INTRODUCED'` 만 봤다. 게이트가 있던
동안에는 `연결 → 종료` 2단 조작이라 눈에 띄지 않았지만, 종료가 주선자의 **유일한**
레버가 된 지금은 목록을 정리하려 누른 버튼이 회원이 보던 연락처를 지운다.

되돌릴 수 없는 것을 되돌리는 척하는 동작이라 판단해 `IN ('INTRODUCED','CLOSED')` 로
바꿨다(0022). 종료는 주선자의 정리 행위이고 공개 철회가 아니다. 판정이 RLS 와
애플리케이션에 두 벌 있으므로 **양쪽을 함께** 고쳤다 — `tests/rls.test.ts` 가
네 상태를 훑어 갈라지지 않는지 지킨다.

**초대 발급에 프로필 권한 검사가 없었다.** `/api/admin/invites` 가 `requireAdmin()`
만 하고 대상 프로필을 누가 관리하는지 보지 않았다. `invites` 정책은 이미
`app_can_edit_profile(profile_id)` 를 요구하지만 `issueInvite` 는 owner 커넥션이라
정책을 지나간다.

주선자 가입이 열려 있어 실제로 체인이 완성됐다 — `/signup` 으로 아무나 주선자가 되고,
남이 등록한 **이미 주인이 있는** 프로필에 초대를 발급하고, 그 링크로 그 회원 계정에
로그인된다(`firstTime:false`). 매직 링크가 곧 자격 증명이므로 완전한 계정 사칭이고,
그 회원이 연결된 모든 상대의 실명·연락처가 함께 열린다. 부수로 정상 초대가
`revoked_at` 처리돼 실제 회원의 링크까지 죽는다.

`assertCanEditProfile()` 을 `server/repo/profiles.ts` 에 두고 라우트가 발급 전에
회원 RLS 컨텍스트에서 `app_can_edit_profile` 을 묻게 했다. 「`ADMIN` 이라는 사실만으로
권한을 주지 않는다 / 읽기와 쓰기를 다르게 준다」 규칙을 어기던 유일한 쓰기 경로였다.

## 입장코드와 로그인 화면 분리 (2026-09-08)

초대 링크가 **열리지 않는 회원**이 있었다. 카카오톡에서 받은 링크를 다른 앱으로
옮기거나 인앱 브라우저가 막는 경우다. 링크를 여는 것 말고 들어올 방법이 없어서
주선자가 다시 보내는 것 외에 할 게 없었다.

### 코드는 새로 만들지 않았다

**입장코드는 초대 토큰 그 값 그대로다.** 별도 코드 체계를 만들지 않았다 — 만드는
순간 만료·재사용·회수 판정이 두 벌이 되고, 두 벌이 어긋나면 한쪽으로는 죽은 초대가
살아난다. `POST /api/admin/invites` 가 같은 값을 `url` 과 `code` 두 필드로 내려주고,
회원은 어느 쪽을 써도 같은 `/claim` 경로를 지난다. **하나를 쓰면 다른 하나도 함께
무효가 된다** — 실제로 같은 행이기 때문이다.

`extractInviteCode` 는 링크 전체를 붙여넣어도 토큰만 뽑는다(`/claim/` 뒤, 쿼리·해시·
공백 제거, 인코딩 복원). 형식만 보고 유효성은 판정하지 않는다 — 만료·재사용은 서버
한 곳(`consumeInvite`)에만 있다.

### 두 청중을 한 화면에 섞지 않는다

처음에는 `/login` 한 화면에 주선자 폼과 입장코드 폼을 위아래로 놓았다. 서로가 상대의
폼을 읽어야 해서 둘 다 어려워졌다 — 회원은 자기에게 없는 이메일·비밀번호 칸을 보고,
주선자는 코드 칸을 보고 자기 것인지 헷갈린다.

| 경로      | 청중   | 묻는 것              |
| --------- | ------ | -------------------- |
| `/login`  | 주선자 | 이메일 + 비밀번호    |
| `/enter`  | 회원   | 입장코드 하나        |
| `/signup` | 주선자 | 가입                 |

세 화면의 껍데기는 `components/ui/auth-shell.tsx` 하나로 모았다. 서로를 가리키는
링크가 각 화면 아래에 있어서 잘못 온 사람이 한 번에 건너간다. 초대 링크를 열면
`/enter` 를 거치지 않고 바로 `/claim` 이므로, `/enter` 에 오는 사람은 **코드만 받았거나
세션이 만료된 회원**이다.

`/claim` 이 실패하면 `/enter?code=<입력한 값>` 으로 돌려보낸다. 옮겨 적다 틀린
경우가 대부분이라 빈 칸이 아니라 방금 넣은 값이 들어 있는 칸으로 돌아간다.

### `?next=` 는 검증한다

로그인 뒤 원래 보려던 화면으로 돌아가려면 `?next=` 를 받아야 하는데, 그대로 쓰면
로그인 화면이 **열린 리다이렉터**가 된다. `safeNextPath` 가 같은 출처의 경로만
통과시킨다 — `/` 로 시작하지 않는 값, `//호스트`, `/\호스트` 를 버린다. 뒤 두 개는
브라우저가 다른 출처로 해석하는 형태다.

`tests/auth-links.test.ts` 가 코드 정규화와 이 판정을 함께 지킨다.

## 시드 관리자 비밀번호 (2026-09-08)

`pnpm db:seed` 가 심는 관리자 비밀번호가 이 저장소에 적힌 고정값(`bolsaram-admin`)
이었다. 이 호스트의 값은 2026-09-07 에 교체했지만 **원인은 그대로 남아 있었다** —
새로 시드한 환경을 공개 주소에 붙이는 순간 같은 일이 다시 일어난다. 시도
제한(15분 5회)은 이미 알려진 비밀번호를 막지 못한다.

고정값을 없앴다. `SEED_ADMIN_PASSWORD` 를 주면 그 값(가입과 같은 10자 이상)을 쓰고,
없으면 `randomBytes(12)` 의 base64url 16자를 만들어 **시드 실행 결과에 한 번만**
출력한다.

**이미 있는 계정의 비밀번호는 건드리지 않는다.** 전에는 `ON CONFLICT DO UPDATE SET
password_hash` 라서 시드를 다시 돌리면 운영 중 교체한 값이 문서화된 기본값으로
되돌아갔다. 이제 계정 존재를 먼저 확인하고, 새로 만들 때만 값을 정한다.
`SEED_ADMIN_PASSWORD` 를 명시적으로 준 경우에만 기존 계정의 값을 교체한다 — 값을
잃었을 때 되찾는 경로가 필요하다.

판정만 `cli/seed-admin-password.ts` 로 떼어냈다. `seed.ts` 는 import 만으로 시드가
돌아서 테스트가 붙을 수 없다. `tests/seed-admin-password.test.ts` 가 옛 기본값이
다시 나오지 않는 것, 생성값이 가입 최소 길이를 넘는 것, 짧은 환경변수를 거부하는
것을 지킨다.

`run-web` 스킬의 확인용 로그인도 고쳤다. 저장소에 비밀번호가 없으므로 점검이
필요하면 `/api/auth/signup` 으로 임의 비밀번호의 확인용 주선자를 만들어 쓴다.

## 방침을 화면에 걸었다 — `/privacy` (2026-09-08)

문서만 있고 회원이 열어볼 경로가 없으면 **고지한 것이 아니다.** `docs/guide/privacy.md`
를 그대로 보여주는 라우트를 붙였다.

### 문서를 다시 쓰지 않았다

화면용으로 같은 내용을 JSX 에 옮겨 적으면 둘이 갈라진다. 방침에서 그것은 그냥 틀린
문장이고, 어느 쪽이 진짜인지 아무도 모른다. 그래서 **문서가 단일 원본**이고 화면이
그것을 읽는다. 문구·표현은 테스트로 지킬 수 없으니 구조적으로 하나만 두는 쪽을 골랐다.

### 마크다운 의존성을 더하지 않았다

가이드 문서가 쓰는 문법은 좁다 — 제목·문단·강조·인라인 코드·인용·표·목록·구분선.
링크도 이미지도 코드 블록도 없다. `lib/markdown.ts` 가 이 부분집합만 **블록 배열**로
파싱하고, `components/ui/markdown.tsx` 가 그것을 그린다.

파서를 JSX 와 분리한 이유는 테스트다. 블록 배열까지만 만들면 렌더링 없이 문서 전체를
훑을 수 있다. `tests/markdown.test.ts` 가 지키는 것 —

- 표·인용·목록·구분선이 실제로 인식되는가 (문단으로 삼켜지지 않는가)
- 문서가 **파서가 모르는 문법**을 쓰기 시작하지 않았는가 (링크·이미지·코드 블록·중첩 목록)
- `**` 나 `` ` `` 같은 표시 문자가 본문에 남지 않는가
- 소프트 줄바꿈이 공백이 되므로 **중점이나 여는 괄호에서 줄을 끊지 않았는가**

마지막 항목은 실제로 걸렸다. 「상호·」 로 줄을 끊어 놨더니 화면에서 「상호· 사업자등록
번호」로 벌어진다. 문서를 다시 감았다.

### 로그인을 요구하지 않는다

무엇을 모으는지 읽어야 들어올지 정할 수 있다. 이 화면에는 회원 정보가 없으므로
비로그인 접근을 막지 않는다. 첫 화면·로그인·입장·가입 화면(`AuthShell`)과 회원의
「내 프로필」 아래에 링크를 뒀다.

`force-static` 으로 빌드 때 한 번 읽는다. **문서를 고치면 빌드해야 화면에 반영된다** —
턴 종료 훅이 빌드하므로 평소에는 저절로 맞는다.

### 남은 것

- **법률 검토와 시행일.** 화면에는 「법률 검토를 받지 않았습니다」 경고가 그대로
  보인다. 실회원을 받기 전에 검토를 받고 그 문장과 시행일을 함께 정리한다.
- 나머지 가이드(`member.md`·`admin.md`·`faq.md`)도 같은 방식으로 화면에 걸 수 있지만
  붙이지 않았다. 회원이 지금 묻는 것은 방침이고, 화면 안내는 각 화면에 이미 있다.

## 거절 이후를 정비했다 — 재신청 금지 · 숨기기 (2026-09-08)

거절은 상태 하나만 남기고 끝났다. 활성 신청(`REQUESTED`·`INTRODUCED`)만 중복을 막았기
때문에, 거절당한 사람은 **곧바로 다시** 마음을 보낼 수 있었고 탐색 목록에도 그 사람이
계속 떴다. 받는 쪽은 같은 사람에게 반복해서 거절을 눌러야 했다.

### 정한 것

| 축         | 정한 것                                                          |
| ---------- | ---------------------------------------------------------------- |
| 재신청     | **완전 금지.** 대기 기간이나 횟수 상한을 두지 않았다             |
| 탐색 제외  | **거절 관계 양방향.** 연결 종료(`CLOSED`)는 빼지 않는다          |
| 숨기기     | 회원이 직접 숨긴다. **신고는 만들지 않았다**                     |

완전 금지를 고른 이유는 상태만으로 판정이 끝나기 때문이다. 대기 기간을 두면 "언제부터
다시 보낼 수 있는지" 를 화면에 설명해야 하고, 그 시각을 계산하는 코드가 도메인·DB·UI 에
각각 생긴다. 거절을 존중하는 서비스에서 그만한 복잡도를 살 이유가 없었다.

양방향으로 만든 이유는 한쪽만 막으면 상태가 어긋나기 때문이다. A 가 B 를 거절했는데
A→B 신청이 열려 있으면, 목록에서는 서로 안 보이는데 상세 URL 로는 신청이 되는
모순이 생긴다.

`CLOSED` 를 빼지 않은 것은 의도다 — 주선자가 마무리한 건이고 이름·연락처는 이미
공개돼 있다(0022). 목록에서 지운다고 정리되지 않는다.

### 재신청 금지를 인덱스가 아니라 트리거로 막았다

`match_requests_one_active` 부분 유니크 인덱스를 `REJECTED` 까지 넓히는 것이 자연스러워
보이지만, **이미 쌓인 이력이 같은 방향으로 둘 이상이면 인덱스 생성 자체가 실패한다.**
맞추려면 과거 신청 기록을 지워야 한다. 트리거는 새 삽입만 보므로 이력을 건드리지 않고,
방향을 구분하지 않는 조건도 그대로 쓸 수 있다(유니크 인덱스는 방향별로만 잡힌다).

### 숨김은 방향을 알려주지 않는다

`profile_hides` 의 RLS 는 **숨긴 사람에게만** 행을 보여준다. 상대에게도, 주선자에게도
정책을 주지 않았다. 그러면 "상대가 나를 숨겼는가" 를 알 수 없어 신청을 막을 수 없으므로,
판정만 내보내는 `SECURITY DEFINER` 함수를 뒀다 — `app_is_hidden_between()` 은 boolean 하나만
돌려주고 누가 숨겼는지는 드러내지 않는다.

같은 이유로 화면 문구도 방향을 담지 않는다. 거절과 숨김이 겹쳤을 때 「거절」이라고
답하면, 거절한 적이 없는 쪽이 **상대가 숨겼다는 사실을 역산할 수 있다.** 그래서
`assertCanCreateRequest` 는 숨김을 거절보다 먼저 본다.

### 탐색 제외를 함수 하나로 모았다

프로필마다 판정 함수를 부르면 목록 조회가 행 수만큼 서브쿼리를 돈다.
`app_discover_excluded_profile_ids()` 가 거절·숨김 상대를 한 번에 돌려주고
`buildDiscoverWhere` 가 `NOT IN` 으로 거른다. `STABLE` 이라 쿼리당 한 번만 평가된다.

도메인 필터가 DB 함수를 부르는 것은 이 파일의 다른 조건과 결이 다르지만, 서브쿼리를
직접 쓰면 **RLS 로 보이지 않는 방향(상대가 나를 숨김)이 빠진다.** 정확성을 택했다.

### 신고를 만들지 않았다

숨기기는 조용히 넘기는 장치이고, 신고는 주선자 화면·알림·처리 상태까지 필요한 별개
기능이다. 지금은 문제가 있는 회원을 **회원이 주선자에게 카카오톡으로 알린다** — 등록도
주선자가 손으로 하는 서비스라 그 경로가 이미 있다.

### 검증에서 나온 결함 세 개를 고쳤다

앱을 실제로 띄워 확인하니 첫 구현에 구멍이 세 개 있었다. 전부 같은 턴에 고쳤다.

**1. 되돌릴 수 없는 숨김 (0024)**

0023 은 「숨긴 관계에는 신청할 수 없다」만 막았다. **반대 순서가 열려 있었다** —
신청을 보낸 뒤 숨기면 신청은 `REQUESTED` 로 남고, 상대가 그것을 수락하면 숨긴 사이인데
연결된 상태가 된다. 화면은 연결된 상대에게 숨김 해제를 주지 않으므로 회원이 스스로
되돌릴 수 없었다.

두 규칙이 한 방향만 막고 있었던 것이 원인이다. 0024 가 반대쪽을 막는다 — **활성 신청이
있는 상대는 숨기지 못한다.** 그래서 숨기기는 거절을 대신하지 않는다: 받은 신청은 먼저
거절하고, 보낸 신청은 먼저 취소한 다음 숨긴다. 거절 자체가 재신청을 막으므로 흐름이
겹치지 않는다.

같이 고친 것: 상세 화면이 **이미 숨긴 상대에게는 상태와 무관하게** 해제를 준다.
해제 버튼을 상태로 가리면 같은 종류의 막다른 상태가 다시 생긴다.

**2. 관심 목록에는 제외가 걸려 있지 않았다**

`buildDiscoverWhere` 만 제외 함수를 썼다. 그래서 숨겨진 쪽이 상대를 관심에 담아두면
목록에 남아 있고, 들어가면 비활성 CTA 를 본다. 무관한 제3자에게는 정상 CTA 가 뜨므로
**자기가 숨겨졌다는 것을 추론할 수 있었다.** `favoriteProfileIds` 에 같은 제외를 걸었다.

관심 **행은 지우지 않는다** — 회원이 담아둔 기록이고, 관계가 풀리면 다시 보여야 한다.

남는 한계: URL 을 이미 알고 있으면 상세로 직접 들어가 비활성 CTA 를 볼 수 있다. 이것은
「양방향으로 신청을 막는다」와 「상대는 모른다」가 동시에 완전할 수 없기 때문이고, 문구를
모호하게 두는 것(`지금은 보낼 수 없어요`)까지가 할 수 있는 일이다.

**3. 없는 프로필을 숨기면 500 이었다**

FK·CHECK 위반이 그대로 올라와 `500 INTERNAL` 이 되고, 200/500 의 차이가 「그 uuid 의
프로필이 존재하는가」를 알려줬다. `/api/hides` POST 가 대상을 먼저 조회해
`isDetailAccessible` 로 확인하고, 자기 자신·활성 신청은 도메인 오류로 던진다. 범위 밖
프로필에 숨김 행이 생기던 것도 같이 막혔다.

### 거절과 숨김에 같은 문구를 쓴다

처음에는 문구를 갈랐다 — 거절은 「다시 보낼 수 없어요」, 숨김은 「지금은 보낼 수
없어요」. 재검증에서 이것이 새는 것을 확인했다. **자기가 거절한 사실을 아는 사람**이
「다시」가 아닌 답을 받으면, 거절 말고 다른 것이 걸려 있다는 뜻이므로 상대가 자기를
숨겼음을 추론할 수 있다.

그래서 두 이유에 `CANNOT_REQUEST_MESSAGE` 하나만 쓴다. 도메인 오류와 화면 라벨이 같은
문자열을 본다. **왜 막혔는지는 화면이 설명하지 않고** 가이드가 두 경우를 함께 적는다 —
이유를 구분해 보여주는 것과 숨김을 통보하지 않는 것을 동시에 지킬 수는 없다.

`tests/match-transitions.test.ts` 의 「거절·숨김·둘 다에 같은 문구」가 세 경우의 문구가
글자까지 같은지 본다. 문구를 다시 가르려 하면 여기서 걸린다.

### 남은 것

- **연결된 상대는 숨길 수 없다.** 연락처를 이미 주고받은 뒤라 화면에서 지우는 것으로
  정리되지 않는다. 그런 경우는 주선자가 처리한다. 회원이 직접 끊는 경로는 없다.
- 신고 기능. 위 이유로 미착수다. 실회원 운영에서 필요해지면 그때 만든다.
- **연결된 상대는 탐색 목록에 계속 뜬다.** 0023 의 범위 밖이고, 이미 연락하는 사이라
  목록에서 지우는 것이 옳은지 정하지 않았다.
